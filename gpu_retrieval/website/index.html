GPU Retrieval Pipeline with Parallel Preprocessing and Top-k Selection

For each of Q queries, find the K most similar vectors among N corpus vectors. Normalization, scoring and top-k selection all run on the GPU. Every number below is measured on an RTX 5060 Ti against a 20-thread Core Ultra 7 265K.

Speedups are ranges across corpus sizes N = 65,536 to 2,097,152 (D = 128, Q = 64, K = 10). The CPU reference is a straightforward OpenMP loop. Recall was 1.0000 in all 48 GPU runs.

Top-k without sorting

Sorting every row of N scores does far more work than needed. The custom kernel gives each thread a slice of the row and a private list of the K best values it has seen, then merges the lists with K rounds of picking the largest head. This miniature uses 16 scores, 4 threads and K = 3. Thread T0 reads indexes 0, 4, 8 and 12, thread T1 reads 1, 5, 9 and 13, and so on.

Where the time goes

Stage times for the 64-query run at each corpus size. The CPU does scoring and top-k in one fused loop, so those two are one block there.

The host-to-device copy is the largest GPU cost at every size. Keeping the corpus resident on the GPU between query batches removes it.

Run it yourself

On Windows with WSL2 and an NVIDIA driver, after installing CUDA toolkit 12.8 or newer inside Ubuntu:

make cpu && ./bench_cpu --N 262144 --D 128 --Q 64 --K 10
make gpu ARCH=sm_120 && ./bench_gpu --N 1048576 --D 128 --Q 64 --K 10
bash scripts/sweep.sh && python3 scripts/plot.py

Use the matching ARCH for other cards (for example sm_75 for a T4, sm_80 for an A100).

Limits

  • The same CPU configuration measured 397 to 569 ms across separate runs, while the GPU stayed within 70 to 74 ms. That is why speedups are given as ranges.
  • The data is synthetic random vectors. K is limited to 32. The Q × N score matrix is stored in memory.
  • One machine, one GPU, under WSL2.

Next steps: pinned memory with streams to hide the copy, cuBLAS or tensor cores for scoring, a fused score and top-k kernel, and radix selection for larger K.
